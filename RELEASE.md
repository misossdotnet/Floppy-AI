# Floppy-AI

> Datas Warehouse
> LLM Data Engineering Platform - Dataset Factory

## Application du logiciel

Le logiciel sert de couche de preparation des donnees entre:

- la source de contenu (CMS, Notion, markdown exporte, etc.);
- les pipelines de pre-training / fine-tuning LLM;
- les workflows d'orchestration (n8n, scripts Python, jobs batch).

En pratique, `Floppy-AI` permet:

- de creer des projets et leurs tables dediees;
- de stocker les documents "longs" dans des shards;
- de decouper ces shards en chunks avec overlap;
- de conserver la tracabilite et la qualite des donnees pour l'entrainement des modeles.

## Fonctionnalites principales

1. Creation de projet
   - Saisie du nom dans l'interface.
   - Transformation automatique en slug.
   - Provisioning des tables `{slug}_shard`, `{slug}_chunk`, `{slug}_train`, `{slug}_chat` et `{slug}_chat_evaluation`.
   - Insertion dans `public.project`.
2. Vue projet / shards / chunks / train
   - Affichage des shards par projet.
   - Comptage des chunks relies via `chunk.shard_id = shard.uuid`.
   - Visualisation detaillee des shards et des chunks (metadata + contenu complet).
   - Saisie des exemples de conversation dans `{slug}_train`.
3. Vue chat + evaluation
   - Liste des conversations par `session_id` dans `{slug}_chat`.
   - Visualisation des messages groupes par `session_id`.
   - Formulaire d'evaluation d'une session (5 ratings + commentaire) dans `{slug}_chat_evaluation` (upsert sur `session_id`).
4. Dashboard chat_evaluation
   - KPI qualite (sessions evaluees, score global, moyennes par axe, taux excellentes/problematiques).
   - Evolution hebdomadaire des scores.
   - Relation longueur de session vs score global.
5. Preparation dataset pour pre-training LLM
   - Decoupage prioritaire par sections Markdown (`#`, `##`, `###`).
   - Re-decoupage si depassement de la taille cible.
   - Parametres de tokenisation ajustables.
   - Metadata de contexte (`previous_document_id`, `previous_chunk_id`, `next_chunk_id`, etc.).

## Modele de donnees

Le schema de reference est documente dans [app_skull.sql](docs/app_skull.sql).

### `public.project`

- `uuid text PRIMARY KEY`
- `project_name text`
- `project_nameslug text`
- `last_date_edit timestamptz DEFAULT now() NOT NULL`

### `{slug}_shard`

- `uuid text PRIMARY KEY`
- `project_id text`
- `source_document text`
- `url_document text`
- `title_document text`
- `content_document text`
- `autor_document text`
- `last_date_edit timestamptz DEFAULT now() NOT NULL`

### `{slug}_chunk`

- `uuid text PRIMARY KEY`
- `shard_id text`
- `source_document text`
- `url_document text`
- `title_document text`
- `content_document text`
- `autor_document text`
- `last_date_edit timestamptz DEFAULT now() NOT NULL`

### `{slug}_train`

- `uuid text PRIMARY KEY`
- `project_id text`
- `system_content text`
- `user_content text`
- `assistant_content text`
- `upvote integer`
- `downvote integer`
- `last_date_edit timestamptz DEFAULT now() NOT NULL`

### `{slug}_chat`

- `id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `session_id varchar(255) NOT NULL`
- `message jsonb NOT NULL`
- `upvote integer DEFAULT 0`
- `downvote integer DEFAULT 0`

### `{slug}_chat_evaluation`

- `id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `session_id varchar(255) NOT NULL UNIQUE`
- `rating_relevance smallint CHECK (1..5)`
- `rating_accuracy smallint CHECK (1..5)`
- `rating_clarity smallint CHECK (1..5)`
- `rating_completeness smallint CHECK (1..5)`
- `rating_helpfulness smallint CHECK (1..5)`
- `rating_global numeric(3,2) GENERATED ALWAYS AS average des 5 ratings`
- `comment text`
- `created_at timestamptz DEFAULT now()`
- `updated_at timestamptz DEFAULT now()`

## Flux de traitement (pre-training LLM)

1. Un document est enregistre dans `{slug}_shard`.
2. L'endpoint de chunking lit `content_document`.
3. Le texte est segmente en chunks avec overlap et metadata.
4. Les chunks sont ecrits dans `{slug}_chunk`.
5. Les items retournes sont prets pour un flux de pre-training/fine-tuning (et indexation RAG si necessaire).

Chaque item genere contient:

- `pageContent` / `text`
- `metadata.document_id`
- `metadata.section_title`
- `metadata.section_path`
- `metadata.previous_document_id`
- `metadata.previous_chunk_id`
- `metadata.next_chunk_id`

## Parametres de chunking (defaut)

```json
{
  "chunkMaxTokens": 350,
  "chunkOverlapTokens": 50,
  "hardMaxTokens": 420,
  "headingMaxLevel": 3,
  "tokenEstimator": "words",
  "charsPerToken": 4
}
```

Recommandation generale pour un dataset documentaire LLM:

- `chunkMaxTokens`: 250 a 500
- `chunkOverlapTokens`: 30 a 80
- `headingMaxLevel`: 2 ou 3
- `tokenEstimator`: `words` (suffisant dans la majorite des cas)

## Routes utiles

- `GET /` : creation de projet et vue rapide des composants
- `GET /projects/shards` : vue detaillee projets + shards + compteurs
- `POST /projects/<project_slug>/chunkify` : generation des chunks
- `POST /projects/<project_slug>/train` : ajout d'un item train
- `POST /projects/<project_slug>/delete` : suppression projet + tables dynamiques
- `GET /projects/<project_slug>/shard-list` : liste shards (add/delete/visualisation)
- `POST /projects/<project_slug>/shards/add` : ajout shard
- `POST /projects/<project_slug>/shards/<shard_uuid>/delete` : suppression shard
- `GET /projects/<project_slug>/train-list` : liste train (add/delete)
- `POST /projects/<project_slug>/trains/<train_uuid>/delete` : suppression train
- `POST /projects/<project_slug>/trains/<train_uuid>/vote` : vote train (up/down)
- `GET /projects/<project_slug>/chunk-list` : liste chunks (add/delete/visualisation)
- `POST /projects/<project_slug>/chunks/add` : ajout chunk
- `POST /projects/<project_slug>/chunks/<chunk_uuid>/delete` : suppression chunk
- `GET /projects/<project_slug>/chat-list` : liste sessions chat + detail conversation
- `GET /projects/<project_slug>/chat-dashboard` : KPI et analyses chat_evaluation
- `POST /projects/<project_slug>/chat-evaluations` : creation/mise a jour evaluation par `session_id`
- `GET /health` : healthcheck

Nouvelle couche API orientee "preparation de corpus":

- `POST /projects/<project_slug>/imports` (alias: `/api/v1/projects/<project_slug>/imports`)

- `POST /projects/<project_slug>/build-dataset` (alias: `/api/v1/projects/<project_slug>/build-dataset`)
- `GET /dataset-builds/<build_id>` (alias: `/api/v1/dataset-builds/<build_id>`)
- `GET /chunks?project=<slug>&quality_min=<0..1>&limit=<n>&offset=<n>` (alias: `/api/v1/chunks`)

Objets metier ajoutes:

- `public.document_processing` (normalisation, statut d'approbation, score qualite)
- `public.chunk_metadata` (lineage des chunks et score qualite)
- `public.dataset_build` (historique des builds dataset)

### Authentification API/MCP

Les routes metier sensibles (`imports`, `normalize`, `chunk`, `build-dataset`, `approve`, `mcp`) et les routes UI destructives (`delete`) supportent une authentification par token.

- Header recommande: `Authorization: Bearer <token>`
- Alternative: `X-Floppy-Token: <token>`
- Scopes attendus selon la route: `imports`, `normalize`, `chunk`, `build_dataset`, `approve`, `mcp`, `write`, `delete` (ou `admin`)
- ACL MCP par outil (en plus du scope `mcp`): `floppy.import_documents` -> `imports`, `floppy.normalize_document` -> `normalize`, `floppy.chunk_project` -> `chunk`, `floppy.build_dataset` -> `build_dataset`, `floppy.approve_document` -> `approve`

Validation centralisee des payloads:

- Les operations REST et MCP partagent les memes schemas d'entree (validation type/champs obligatoires/bornes).
- En cas d'entree invalide, la reponse retourne une erreur `validation_error` coherente entre REST et MCP.

Variables d'environnement:

- `APP_ENV` (`development`/`local`/`test` => mode local)
- `FLOPPY_REQUIRE_AUTH` (defaut: `false` en local, `true` hors local)
- `FLOPPY_AUTH_TOKENS` (format JSON ou CSV `token:scope1|scope2`)

### Exemple import de documents

```bash
curl -X POST http://localhost:8000/api/v1/projects/<project_slug>/imports \
  -H "Authorization: Bearer <token-imports>" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": [
      {
        "source_document": "notion",
        "title_document": "Guide API interne",
        "content_document": "# Intro\n\nContenu du document...",
        "autor_document": "ops-team"
      }
    ]
  }'
```

## Version MCP (JSON-RPC HTTP)

Endpoint MCP:

- `GET /mcp` : infos serveur
- `POST /mcp` : transport JSON-RPC 2.0

Methodes supportees:

- `initialize`
- `tools/list`
- `tools/call`

Tools exposes:

- `floppy.import_documents`
- `floppy.normalize_document`
- `floppy.chunk_project`
- `floppy.build_dataset`
- `floppy.get_dataset_build`
- `floppy.search_chunks`
- `floppy.get_document_lineage`
- `floppy.approve_document`

### Exemple MCP `tools/list`

```bash
curl -X POST http://localhost:8000/mcp \
  -H "Authorization: Bearer <token-mcp>" \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {}
  }'
```

### Exemple MCP `tools/call` (build dataset)

```bash
curl -X POST http://localhost:8000/mcp \
  -H "Authorization: Bearer <token-mcp>" \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 2,
    "method": "tools/call",
    "params": {
      "name": "floppy.build_dataset",
      "arguments": {
        "project_slug": "<project_slug>",
        "quality_min": 0.5,
        "limit": 500
      }
    }
  }'
```
